## 1. UDP 遥操作问题 (Follower Cart Mode)

### 1.1 问题现象
- **增量不累积**: 连续发送多次 `+5mm` 增量，机器人只移动一次，无法实现连续长距离移动。
- **坐标轴混乱**: 
  - 发送 `Y+`，机器人实际向 `Z` 轴移动。
  - 发送 `Z+`，机器人实际向 `Y` 轴移动。
  - 方向存在反向情况。
- **保护停机**: 单次发送较大增量（如 20mm）时，触发机器人“加速度过大”错误 (-505)。

### 1.2 原因分析
1.  **协议机制**: `follower_cart` 协议接收的是 **相对于跟随起点的绝对偏移量 (Absolute Offset from Start)**，而不是瞬时增量 (Delta)。如果不累积，每次发 `0.005`，机器人就一直停在 `0.005` 处。
2.  **坐标系定义**: 机器人处于特殊姿态（如 `Rx=225`）时，工具坐标系 (Tool Frame) 的 Y/Z 轴与基座坐标系 (Base Frame) 发生了旋转交换。
3.  **物理限制**: 8ms 周期内发送 20mm 阶跃信号，相当于要求速度 `2.5m/s`，远超物理极限。

### 1.3 解决方案与修复
- **客户端累积**: 在 `RobotController` 中维护 `self.follower_offset`，每次发送前将增量累加。
- **坐标轴重映射 (Mapping)**: 
  - 实施了 **Y/Z 轴交换** 策略。
  - **最终映射关系**:
    - **期望 X** -> 发送给机器人 **X 通道**
    - **期望 Y** -> 发送给机器人 **Z 通道**
    - **期望 Z** -> 发送给机器人 **Y 通道** (且不做反向)
- **安全拦截**: 增加了速度检查，当指令速度 > 0.5m/s 时自动拦截并报警。

## 2. 3D 视图卡顿与通信架构

### 2.1 问题现象
- 当执行长动作（如“画圆轨迹”耗时 5秒）时，3D 界面上的机械臂模型**完全静止**。
- 动作结束后，模型突然跳变到终点。

### 2.2 原因分析
- **单通道阻塞**: 系统只使用了一个 WebSocket 连接 (5999)。
- `move_joint` 指令是**阻塞式**的（等待机器人执行完成才返回）。
- 在阻塞期间，**状态查询指令 (Get Status)** 无法发出，导致 UI 拿不到关节数据。

### 2.3 解决方案：双通道架构
重构了 `RobotController` 和连接逻辑：
1.  **控制通道 (Control Channel)**: 连接 **5999** 端口。负责发送阻塞性指令 (Move, Enable)。
2.  **监控通道 (Monitor Channel)**: 连接 **5888** 端口。负责以 **30Hz** 频率高频读取机器人状态。
3.  **效果**: 即使控制通道在等待动作完成，监控通道依然流畅运行，3D 视图实现了丝滑的实时同步。

## 3. IK 逆运动学性能优化

### 3.1 问题现象
- 使用 Python 库 `roboticstoolbox` (RTB) 的 `ikine_LM` 求解器。
- 单次解算耗时 **7ms ~ 15ms**。
- 虽然对于低频控制够用，但对于 125Hz (8ms) 的高频视觉伺服来说，计算占用了太多时间窗口。

### 3.2 优化方案：C++ 后端集成
- **引入 PyBullet**: 使用其内置的 C++ 逆运动学求解器。
- **模型校准**: 
  - 发现 SolidWorks 导出的 URDF (`urdf_export_fine`) 与 RTB 的 DH 参数不一致（误差 > 50mm）。
  - 编写 `fast_ik/generate_urdf.py`，根据 DH 参数**重新生成**了标准的 `ka_ur.urdf`。
- **结果**:
  - 精度误差 < **0.05mm**。
  - 解算耗时降至 **0.3ms** (提升约 30 倍)。

## 5. 遗留/待观察事项

1.  **坐标系依赖性**: 目前的 Y/Z 交换是基于特定工装姿态的。如果更换末端工具或改变手眼标定，可能需要重新调整映射。
2.  **网络抖动**: 8ms 的 UDP 发送频率对网络稳定性要求较高。如果出现丢包，机器人可能会有轻微顿挫（机器人底层通常有插补平滑，影响不大）。

## 6. UDP 轨迹执行显示数据异常

### 6.1 问题现象
- 在终端打印的“UDP 轨迹执行性能报告”中，“偏移 X(mm)” 和 “偏移 Y(mm)” 的数据列输出反了。
- 示教器 UI 界面左侧的“线性偏差”在 UDP 增量轨迹执行期间一直保持为 0 或者不更新。

### 6.2 原因分析
- **终端打印列反转**: 发送给控制器的 UDP 指令为了匹配机器人坐标系做了 `dx` 和 `dy` 的对调，但在 `print` 格式化输出时，误将代表 Y 轴增量的 `delta[1]` 放到了 X 列，将 `delta[0]` 放到了 Y 列。
- **UI 偏差不更新**: 在 `_run_points_sequence_udp` 循环体内，未能将当前解析到的目标点 `p` 赋值给内部状态变量 `self.current_target_point`。UI 刷新线程在计算当前 TCP 和目标点欧氏距离时，因目标点未更新导致无法正确计算动态误差。

### 6.3 解决方案与修复
- 修正了 `main_window.py` 中 `print(f"{i:<8} | {delta[0]:<12.2f} | {delta[1]:<12.2f} | ...)` 的变量索引顺序。
- 在 UDP 执行循环中增加了 `self.current_target_point = p` 状态同步，确保主 UI 的渲染线程能够实时拿到最新的期望目标点，进而正确算出“线性偏差（欧氏距离）”。
