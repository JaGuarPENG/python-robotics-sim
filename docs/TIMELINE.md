# 视觉伺服系统延迟与前馈时间线分析

本文档详细描述了在 60Hz 动态追踪系统中，从“小球移动”到“机械臂触碰”这一完整物理过程中的时间线。这有助于理解为什么“计算必须在两帧内完成”，但“系统延迟会跨越多个帧”，以及前馈补偿（Feedforward）如何解决这个问题。

## 1. 核心概念对比

| 概念 | 耗时 | 描述 | 决定了什么 |
| :--- | :--- | :--- | :--- |
| **控制帧周期 (Loop Interval)** | `16.7 ms` (60Hz) | Python `_tracking_loop` 两次循环之间的时间间隔。 | 系统发指令的“射速”。只要**单次计算耗时 < 16.7ms**，程序就不会卡顿。 |
| **单次计算耗时 (Compute Time)** | `~2-5 ms` | 执行 IK 逆解和将指令写入网卡的时间。 | 它完全包含在 16.7ms 的帧周期内。 |
| **系统总物理延迟 (System Latency)** | `~100-200 ms` | 从“相机曝光看到画面”到“机械臂最终到达该画面指定的物理位置”的总时间。 | 它是跨越多帧的。决定了机械臂如果不加预测，会永远落后小球多远。 |

假设当前处于第 N 帧 (T = 0ms)，此时小球正好经过坐标 `Y = 100mm`。

```mermaid
    局域网传输指令         :d1, 00:00:00.019, 0.002s
    控制器底层排队与插补    :d2, after d1, 0.020s
    电机克服惯性开始驱动    :active, d3, after d2, 0.069s
    [到达目标Y=100!]      :milestone, d4, 00:00:00.110, 0.000s
```

### 时间线解读 (悲剧的诞生)
1. **0 ms**: 小球在 `Y=100`，仿真环境瞬间拿到坐标。
2. **16 ms**: 经过极短的 YOLO 计算 (10ms) 和等待下一个 Python 循环，您的程序光速拿到坐标 `Y=100`。
3. **19 ms**: Python 光速算完 IK (2ms) 并发给网卡 (1ms)。**注意：这是非常理想的低延迟上位机！**
4. **110 ms**: 经历了网络传输、工控机插补排队、笨重的铁胳膊加速。机械臂终于在第 110ms 时，“哐当”一声砸在了 `Y=100` 的位置上。
5. **悲剧结果**: 此时小球去了哪里？因为传送带一直在走 (假设 `50mm/s`)，在经过了 110ms 后，小球已经跑到了 `100 + 50 * 0.110 = 105.5mm` 的位置。
6. **结论**: **即使视觉是0延迟（比如使用仿真或者动捕相机），只要机械臂不是0质量的幽灵，纯物理的响应延迟依然会导致永远存在稳态追踪误差！**

## 3. 前馈补偿是如何拯救系统的？

既然我们知道了从“拍下照片”到“手砸下去”必然存在 `~160ms` 的跨帧延迟，我们就可以在 Python 代码里**“预判你的预判”**。

在 `conveyor_tracking_service.py` 中：

```python
# 总前馈时间 = 算法预瞄时间 + 隐性物理系统延迟
# 例如: 50ms + 110ms = 160ms (0.16s)
total_latency_seconds = (self.loop_interval * self.look_ahead_frames) + self.system_latency_offset

# 直接让机械臂去 "未来" 的位置
predicted_target_y = target_pos[1] + (self.conveyor_speed_y * total_latency_seconds)
```

### 补偿后的时间线：
1. **0 ms**: 小球在 `Y=100`，相机拍下。
2. **66 ms**: Python 拿到 `Y=100`。
3. **69 ms**: Python 开始算命：*“等我这笨手砸下去，已经是 160ms 之后了。那时候小球会在哪？会在 `100 + 50*0.16 = 108` 处！”* 于是 Python 发出指令：**“全军出击，目标 Y=108！”**
4. **160 ms**: 机械臂历经千辛万苦，到达了 `Y=108` 的位置。
5. **完美结局**: 而在这个瞬间，小球也刚好滚到了 `Y=108`。**机械臂和小球完美相撞，误差为 0mm！**

## 4. 为什么盲抓 (Blind Tracking) 需要锁定？

在最后的 `APPROACHING` (下压) 阶段，机械臂离小球非常近，相机可能被遮挡，或者下压的震动会导致 YOLO 识别出的 `target_pos` 乱跳。

如果不锁定：Python 会在 `69ms` 时拿到一个飘忽不定的坐标，算出一个飘忽不定的预测点，导致机械臂在下降过程中“疯狂哆嗦”。

**锁定后 (您的最新代码)**：
在 `HOVERING` 阶段一旦对准（找到了完美的 `system_latency_offset`），就**闭上眼睛，不再听信相机的坐标**。利用传送带已知的匀速运动，在本地纯数学累加 `Y`。这样发给机械臂的指令就是一条绝对平滑的直线，机械臂会如丝般顺滑地垂直砸向小球。
